zkAPI v2 uses a **state-anchor chain**: each accepted authorization consumes
the user's current private spend state and leads to a fresh state signed by
the server. The current circuit revision is `zkapi-v2-concession-v1`, using
Groth16 proofs on BN254 and Schnorr signatures on Baby-JubJub.

## Primitives

| Symbol | Meaning |
|---|---|
| `s` | User secret |
| `R` | Registration commitment `Poseidon("zkapi.v2.reg", s, 0)` |
| `D` | Native SOL deposit in integer lamports |
| `L` | Active note leaf `Poseidon("zkapi.v2.leaf", note_id, R, D, expiry)` |
| `B` | Current private available balance |
| `C(B, r, L)` | Note-bound commitment `B·G + r·H + L·J` |
| `τ` | Current state anchor |
| `σ_state` | Server Schnorr signature binding the deployment, commitment, and anchor |
| `x` | Note-bound state nullifier `Poseidon("zkapi.v2c.null", s, note_id, τ)` |
| `σ_clear` | Separate server Schnorr signature authorizing withdrawal of that nullifier |

The strings in these formulas denote domain tags encoded as field elements.
See [Cryptography](/docs/cryptography) for the exact primitives and public inputs.

## Registration

1. The wallet samples `s` and computes `R`.
2. The user deposits `D` into the vault with a Merkle path for its next empty slot.
3. The vault records the deposit and expiry, and inserts the full note leaf `L`
   into its depth-32 Poseidon tree.
4. The wallet initializes `B = D`, `τ = 1`, and a random blinding `r`. Genesis
   requires no server signature; the circuit enforces the initial balance and anchor.

The Solana-default vault uses integer lamports and requires exactly `D`
lamports. The proof statement treats credits as integers and does not embed an
asset conversion. EVM compatibility interprets one credit as one gwei.

## Why the commitment includes the note

Both request and withdrawal circuits compute `L` from the same values used
for Merkle membership, then require the signed commitment to open as
`B·G + r·H + L·J`. The independently derived generator `J` binds that state to
one note, preventing a signed balance from being transplanted to another
active note.

The server can update the commitment without learning `L`. Rerandomization
changes its blinding while retaining the note term. The circuit and setup keys
must support this note binding; the v2 JSON schema and public-input order
alone do not establish circuit compatibility.

## Per-request flow

The wallet generates a fresh rerandomization `ε`, yielding
`C_anon = C(B, r, L) + ε·H`. Its Groth16 request proof establishes:

- membership of the note in the supplied active root;
- a valid genesis state or server-signed current state for that same note;
- `B ≥ solvency_bound` and an expiry at least public `request_time`;
- correct derivation of `x` from the secret, note ID and current anchor, and that
  the anchor chains from the previous nullifier;
- correct rerandomization of the note-bound commitment;
- an authorization tag binding `x` to the request ID and payload hash.

The server recomputes the hash of the exact payload bytes and the request
context, verifies the authorization tag, deployment, signing key, root,
freshness, solvency bound, and proof, then reserves the nullifier. Since `x`
does not depend on the payload, changing the request cannot create another
spendable nullifier for the same state. Exact retries use the durable request
record for recovery.

When usage is finalized, the server applies the charge `Δ` within the
applicable cap and returns a fresh Schnorr-signed state:

```text
C_new = C_anon − Δ·G + blind_delta·H
B_new = B − Δ
r_new = r + ε + blind_delta
τ_new = Poseidon("zkapi.v2c.anchor", x)
```

The signature covers the protocol version, chain, vault address, `C_new`, and
`τ_new`. The wallet verifies the response hash, charge, signature, and commitment
update before saving its next private state and clearing the pending journal.

The browser sends a prompt-free lease authorization to
`POST /v2/openrouter/leases`, uses the leased key directly with OpenRouter, and
obtains its next signed state after retirement and usage settlement. The
accepted native-SOL Pyth quote is part of the proof-bound authorization and
stays fixed through recovery and settlement. The billing server does not proxy
inference requests.

## Refunds

No funds move on-chain per request. Only the actual charge reduces the private
balance; unused capacity under the solvency bound stays available. On close,
the vault settles native SOL:

```text
payout_to_destination = B_final
payout_to_treasury    = D − B_final
```

These ledger amounts are lamports in the Solana backend.
The withdrawal destination is proof-bound and may differ from the funding
address.

## Withdrawal

The withdrawal statement has 16 public inputs: protocol version, chain ID,
vault address, registration, state key (x, y), clearance key (x, y), packed note
fields `(note_id, D, expiry)`, final balance, destination, withdrawal nullifier,
has-clearance, next nullifier, conceded amount, and `valid_until`. It carries no
Merkle path, root or withdrawal tag: the circuit recomputes `R` and `L` from the
range-checked note fields and the vault compares them with the stored note, so
exits are leaf-bound and root-free and no deposit can front-run them. The proof
shows `B = final + c` without wrap, `B ≤ D`, and the note-bound nullifier chain.
`valid_until` is a short TTL bounding how long a prepared proof can be submitted.

**Mutual close.** The wallet requests clearance for its current nullifier from
`POST /v2/withdraw/clearance`. The server reserves the nullifier and returns a
Schnorr signature under its separate clearance key. The wallet includes that
signature as a private witness to the withdrawal proof, then submits the
`execute_close` instruction with `next_nullifier = 0` and `conceded = 0`. The
vault checks its immutable deployment keys, note fields and the Groth16 proof,
consumes the nullifier, pays out and marks the note `Closed`. The leaf stays
until the permissionless, `Closed`-only `retire_closed_leaf` (EVM
`retireClosedLeaf`) removes it.

**Escape hatch.** Without clearance, the wallet submits `execute_escape`. The
vault consumes the state nullifier `N` and the derived successor nullifier
`N+ = nullifier(s, note_id, anchor')` with `anchor' = Poseidon(domain_anchor, N)`,
and records a pending withdrawal paying `final = B − c`. The leaf is not
removed. The challenge window is the vault's configured `challengePeriod`; the
default is 24 hours.

**Challenge.** There is no second phase and no restore. If the escaped state was
already spent, `N+` is the request nullifier of its successor:

- *Defeat:* a challenger supplies a valid request proof whose nullifier equals
  `N+`. The payout is cancelled, `N` becomes challenged, `N+` is released and the
  note stays `Active`. The request proof is verified without any root check, so
  root changes cannot front-run it.
- *Raise:* a challenger supplies a request proof at the escaped nullifier `N`;
  the concession rises to `min(amount, sb, B)` where `sb` is the request's
  solvency bound, and must exceed `c`. The payout becomes `B` minus that value;
  the deadline is unchanged and a defeat remains possible.
- *Finalize:* `finalize_escape(note_id)` is permissionless after the deadline.

Nullifier states: `0` unused or released, `1` consumed, `2` challenged.

**Concession rule and guarantees.** Let `S_k` be the newest state the client
installed and `b_k` the single bound it released at `S_k`.

- **G1 (honest user).** Without operator cooperation the user is paid at least
  `B_k − b_k`. Withholding the successor, front-running deposits, or pausing
  cannot take the unspent balance.
- **G2 (honest operator).** Total paid on a note is at most
  `D − Σ owed(served requests)`. A user who received and spent `S_{k+1}` cannot
  be paid from `S_k`.
- **G3 (privacy).** Requests stay unlinkable. New linkage appears only at exit,
  only for the exiting note, and only for its last request.

**Client exit rules.** The wallet freezes the note when an exit starts, releases
at most one bound per state (re-proving an unfinished lease reuses the recorded
bound), and picks the concession: `c = 0` for a fresh state; for a request in
flight, it waits until the settlement deadline plus a margin or `expiry − 12h`
and then concedes the recorded bound or the smaller reported charge. A signed
successor that fails the derived-anchor check is treated as withheld.

**Server.** The server signs a successor only after the request nullifier is
confirmed unused on the ledger (settle-then-sign) and stores request evidence
in an append-only table; a request whose nullifier an escape consumed is signed
later only if a defeat released it.

**Bounded pause.** The vault pause lasts at most `MAX_PAUSE_DURATION` (7 days)
with a `PAUSE_COOLDOWN` of 1 day. Challenge, raise and finalize are never
blocked. `claim_expired` is blocked while paused and paused time extends the
note's `claimable_at`.

An active note that expires without close-out can be claimed for the treasury
with `execute_claim_expired` (no transition proof) after `claimable_at`.

## Compatibility and trust

Use matching note-bound circuits, proving/verifying keys, browser WASM, and
deployed verifiers. The vault's proof adapter and signing keys are immutable;
client configuration must pin their deployed values. The SDK supports native
SOL by default, keeps EVM/native-ETH state explicitly tagged as compatibility
data, and rejects incompatible wallet formats without relabeling them.

The current elliptic-curve construction is **not post-quantum**. The checked-in
setup is single-party; no multiparty ceremony has been conducted.
Read the [setup and compatibility requirements](/docs/cryptography#setup-and-compatibility)
before choosing deployment artifacts.
